# PeerProof 产品说明（给设计师）

写给接手视觉设计的人。每一屏都有手机版和电脑版截图、这一屏存在的理由、每个输入框和模块的含义。

截图在 `docs/screens/`，文件名规则 `序号-页面-mobile/desktop.png`。手机 390×844，电脑 1280×900，都是真实数据渲染的，不是占位图。

---

## 一、这个产品在做什么

活动报名时交一笔押金。到了现场，参与者**互相扫码作证**，合约自动结算：被证明到场的人拿回押金，**外加缺席者押金的分成**。

**主办方没有任何一个函数可以放款、扣款或收款。** 这是整个产品的立足点——不是「我们承诺不作恶」，是「代码里没有作恶的入口」。

### 为什么扫码能代表「到场」

三重约束叠加：

1. **对方的码 15 秒一换** —— 截图转发过去，两轮就废了
2. **每次见证必须附带场地信标签名** —— 会场屏幕上的码 2 分钟一换，你得在现场读到屏幕
3. **要被确认到场，你自己必须也给别人作过证** —— 所以每个被判定到场的账号，手里都握过一个活着的场地信标

远程串通不是不可能，但代价从零变成了「至少得有一个同伙真的到场并实时转发」。

| 角色 | 用哪些屏 | 在什么设备上 |

| **参与者** | 活动列表 → 活动详情 → 签到 | 手机 |

## 三、逐屏说明

### 1. 活动列表 `/events` —— 首页

![手机](screens/01-events-mobile.png)
![电脑](screens/01-events-desktop.png)

**这一屏回答**：现在有什么活动可以参加。

**模块**

| 模块 | 内容 | 说明 |
|---|---|---|
| 顶栏 | `PEERPROOF` + `Events` + `host one` | `host one` 去主办方后台。**任何人都能办活动，没有审核** |
| 分区标题 | `OPEN NOW` | 只有能参加的排在这里 |
| 活动卡片 | 标题 / 简介 / 状态标签 / 四项数据 | 整张卡可点，进入活动详情 |
| 已结束折叠区 | `N finished events` | **收起但不删除**——公开记录是这个产品的论据，藏起来等于藏证据 |
| 底部说明 | 标题来自不持有资金的合约 | 解释为什么标题可以随便写也不影响钱 |

**状态标签五种**

| 标签 | 含义 | 能否报名 |
|---|---|---|
| `Registering` | 报名中 | ✅ |
| `Starts soon` | 报名已截止，等见证窗口 | ❌ |
| `Checking in now` | 见证窗口开放，正在签到 | ❌（已报名的人去签到屏） |
| `Finished` | 结束，等结算 | ❌ |
| `Cancelled — refunded` | 人数不足，全额退款 | ❌ |
| `Settled` | 已结算 | ❌ |

**卡片上的四项数据**

- `50 MON to join` —— 押金
- `0/8 registered` —— 已报名 / 上限
- `2 vouches to count as present` —— 需要几个人给你作证
- `closes in 1d 4h` —— 倒计时

还有一行条件文案：`Needs 3 more to run — everyone is refunded otherwise`。**人数不够会全额退款**，这句消除报名者的顾虑。

**设计要点**：这是产品门面。卡片密度、状态标签的视觉权重、空状态的样子，都在这一屏定调。

### 2. 活动详情 `/?event=N` —— 未登录

![手机](screens/02-event-mobile.png)
![电脑](screens/02-event-desktop.png)

**这一屏回答**：这个活动是什么，押多少钱，规则是什么。

**模块**

| 模块 | 内容 |
|---|---|
| 标题 + 简介 | 链上读的，主办方写的 |
| 固定说明 | 「押一笔钱占位。到场、给周围的人作证，合约把钱还你——外加缺席者留下的那份」 |
| 三个数字块 | 已报名 / 需要几次见证 / 最低开办人数 |
| 押金卡 | 大字押金额 + 「由合约持有，不是主办方」+ 到场/缺席两种结果 |
| **身份选择区** | 见下 |
| 底部 | 「到场与否由房间里的人决定，主办方没有任何函数能放款、扣款、收款——**自己去查**」 |

**身份选择区**（未登录时）

三条路，按「对多少人有用」排序：

1. **`Create my key`** —— passkey（刷脸/指纹）。**体验最好**：一次授权，之后全程无弹窗
2. **`Continue with email`** —— 邮箱登录，Privy 自动创建钱包。**唯一不需要任何前置条件的路**
3. **`Use a wallet`** —— 已有 MetaMask 的人

**设计要点**：第 1 条不是所有设备都支持（桌面 Chrome、UC 浏览器都没有 WebAuthn PRF）。检测不到时这一屏会变成黄色提示 + 邮箱按钮优先。**这个降级状态要设计，它出现的频率不低。**

### 3. 活动详情 —— 已登录

![手机](screens/03-event-signed-in-mobile.png)
![电脑](screens/03-event-signed-in-desktop.png)

登录后身份选择区变成**一个主按钮**：

```
[ Stake 50 MON and register ]
balance 0.0000 MON  ·  you never see a gas prompt
```

按钮下面那行是**余额和承诺**。「you never see a gas prompt」是 passkey 路径的卖点——派生出的密钥静默签名，不弹窗。

**余额不足时**（见第 9 屏）按钮会禁用，上方出现一块橙色提示，说明还差多少、为什么押金不能由平台代付，并给出获取途径。

### 4. 主办方后台 —— 看板 `/organizer`

![手机](screens/04-organizer-dashboard-mobile.png)
![电脑](screens/04-organizer-dashboard-desktop.png)

**这一屏回答**：我的活动现在什么情况。

| 模块 | 内容 |
|---|---|
| 标签切换 | `Dashboard` / `New Event` |
| 四个数据块 | 已报名 / 已确认到场 / 托管中的金额 / 当前阶段 |
| 参数卡 | 押金、最低人数、需要几次见证、状态 |
| **PAYOUTS 虚线框** | 「结算是自动的。你无法放款也无法扣款」 |
| 兜底签到区 | **只在同伴见证失败时才出现** |

**`Held in escrow` 下面写着 `not in your wallet`** —— 这不是装饰，是整个产品要传达的核心。

**PAYOUTS 那个虚线框是刻意的空状态**：它描述的是「这里没有按钮」。demo 视频里有一个镜头专门停在这。**设计时别把它做成一个看起来可点的东西。**

**兜底签到区**（黄色警告块）只在「到场人数太少、同伴之间凑不够见证」时才解锁。这是**唯一**主办方的话有分量的分支，而且**依然不能让他拿到钱**。健康的活动里这一整块是不存在的。

### 5. 主办方后台 —— 建活动

![手机](screens/05-organizer-new-mobile.png)
![电脑](screens/05-organizer-new-desktop.png)

**六个数字 + 三个文字字段。**

| 字段 | 含义 | 注意 |
|---|---|---|
| `DEPOSIT (MON)` | 每人押金 | |
| `CAPACITY` | 人数上限 | |
| `RUNS IF AT LEAST` | 最低开办人数 | ⚠️ **必须大于下面的 VOUCHES**，否则合约拒绝 |
| `VOUCHES NEEDED` | 需要几个人作证才算到场 | 3 是常用值 |
| `REGISTRATION (MINS)` | 报名窗口多长 | |
| `WINDOW (MINS)` | 见证窗口多长，**在报名截止后才开始** | |
| `Title` | 活动名 | 存在第二个合约里 |
| `Description` | 简介 | 最多 600 字符 |
| `Link (optional)` | 详情页链接 | |

**时序容易误解**：报名窗口结束 → 见证窗口才开始。两者不重叠。界面上应该把这个时间轴画出来，现在只有两个数字输入框，用户很容易以为它们是并行的。

**建完之后**会显示一次性的**场地信标密钥**，要复制到会场那台设备上。这一屏也要设计——它是个「只显示一次、必须复制走」的关键时刻。

### 6. 签到屏 `/floor` —— 手机专用

![手机](screens/06-floor-mobile.png)
![电脑](screens/06-floor-desktop.png)

**这一屏回答**：我怎么证明我到了。

**这是唯一一个刻意锁死手机宽度的屏**——在电脑上打开也是一条窄栏，因为它只会被举在手里用。

| 模块 | 内容 |
|---|---|
| 自己的二维码 | 给别人扫的，**15 秒一换** |
| 倒计时环 | 「refreshes in 12s」+ 一个走针的圆环 |
| `Scan someone` | 扫别人的码 |
| `Scan venue` | 扫会场大屏的码，成功后变成 `Venue ✓` |
| 见证进度 | 收到几个 / 需要几个 |

**两个按钮的视觉层级是有讲究的**：没扫过场地码时，`Scan venue` 是**橙色警告色**，因为没有它，扫人是无效的。扫到之后变灰、打勾。

**使用环境**：站着、单手、房间光线可能很暗、摄像头开着。**触控目标 44px 起**，重要元素别贴在屏幕最底部。

### 7. 场地信标 `/venue`

![手机](screens/07-venue-mobile.png)
![电脑](screens/07-venue-desktop.png)

**这一屏回答**：证明「这件事发生在这个房间里」。

摆在门口的那块屏幕。显示一个**每 2 分钟更换的大二维码**，参与者扫它来证明自己在现场。

| 状态 | 内容 |
|---|---|
| 未配置 | 一个输入框，粘贴信标密钥 |
| 运行中 | 大二维码 + 「Scan me to check in」+ 倒计时 + `forget this key` |

**它会跑在什么设备上不确定**——可能是备用手机，可能是笔记本，可能是投影仪。所以它**不能锁死手机宽度**：二维码要跟着屏幕放大（最大到视口高度的 70%），否则投出来隔几米就扫不到。

**设计要点**：这块屏幕会被远距离观看。字要大，对比要强，二维码周围留白要够。这是唯一一个「不给持有者看、给房间看」的屏。

### 8. 公开记录 `/verify`

![手机](screens/08-verify-mobile.png)
![电脑](screens/08-verify-desktop.png)

**这一屏回答**：凭什么相信结果。

| 模块 | 内容 |
|---|---|
| 见证关系图 | 每个点是一个人，**每条线是一笔真实交易** |
| 图例 | 实心=确认到场 / 空心=报名但未确认 / 数字=收到的见证数 |
| 参与者列表 | 地址 + 状态（present / forfeited） |
| 结算算式 | 每人分到多少，链接到结算交易 |
| 底部 | 合约地址 + 扫描的区块范围 |

**关系图是这个产品的论据本身**。它不是数据可视化装饰——它是「不用相信我们，每条线都能在区块浏览器上查到」的证据。

**设计要点**：这一屏要经得起评委点开逐条核对。节点密集时（50 人）的布局、线条交叉的可读性，是设计难点。

### 9. 余额不足 —— 活动详情的一个状态

![手机](screens/09-funding-mobile.png)
![电脑](screens/09-funding-desktop.png)

**这一屏回答**：我登录了，但我没有钱，怎么办。

这是邮箱登录留下的缺口。Privy 免去了「要有钱包」，但没有免去「要有钱」——一个从没接触过加密货币的人一键拿到账号，然后点报名失败，看起来像产品坏了。

| 元素 | 内容 |
|---|---|
| 橙色提示块 | 「你有 X，需要约 Y，还差 Z」 |
| 解释 | 「押金是你自己的钱进合约，**不能由别人代付**——正是这一点让缺席有代价」 |
| 获取途径 | 测试网：水龙头链接。主网：「从交易所或其他钱包转 MON 过来」 |
| 主按钮 | **禁用** |

**主网上的文案是诚实的**：Monad 的银行卡通道还没开（MoonPay 已建好原生 MON 但处于暂停状态，Stripe 的目标链列表里没有 Monad）。**与其放一个点开什么都买不到的按钮，不如说清楚。**

**设计要点**：这个状态出现的频率会很高——每个用邮箱登录的新用户都会撞上。它不该像错误，该像「下一步做什么」。

### 10. 结算与领款 —— 签到屏的最终状态

![手机](screens/10-payout-mobile.png)
![电脑](screens/10-payout-desktop.png)

**这一屏回答**：我拿到了多少，凭什么。

**这是整个产品的情绪高点**，也是它和所有其他活动报名工具拉开差距的地方——**「到场的人拿回的比投入的多」是一个数字，不是一句承诺**。

截图里是真实的链上结果：4 人报名，3 人到场，1 人缺席。到场的人各拿回 **13.33 MON**（10 押金 + 3.33 缺席者分成）。

| 元素 | 内容 |
|---|---|
| `PAID OUT` | 绿色小标 |
| 大数字 | 到手总额 |
| 拆解 | 「你的 10 MON 押金退回，**外加 3.33 MON** 来自没来的人」 |
| 归属说明 | 「没有人批准这件事。分配比例在窗口关闭时就定死了，由谁给谁作证决定」 |
| 交易链接 | `see the transaction ↗` |

**设计要点**：这一屏之前只是一个变灰的 `Claimed` 按钮。它值得是整个流程里最有分量的一屏——**但分量要来自数字本身和可核验性，不要来自庆祝动效**。这个产品的气质是「你可以查」，不是「恭喜发财」。

上面还有两个模块也在这一屏：

- **`VOUCHED FOR YOU 2/2` + `You count as present`** —— 见证进度，达标后变绿
- **`confirmed present 3/4`** —— 全场进度条

## 四、还没做的部分

原来列了五处缺口，其中三处已经补上（第 9、10 屏，以及充值入口的文案）。剩下两处：

1. **报名成功后的过渡** —— 现在直接变成「去签到屏」，缺一个确认时刻。押金刚离开钱包，这里应该有个交代
2. **见证成功的即时反馈** —— 扫到一个人之后现在只有一个 toast。这是 demo 视频里最关键的镜头（两台设备一秒内同时更新），值得设计得更有存在感

这两处我留着没做，因为它们更依赖视觉判断而不是逻辑——**等你定了整体风格再一起做更合适**。

## 六、给设计的一句话

这个产品的全部主张是「**不用相信任何人，自己验证**」。

所以视觉上应该**克制、可信、像工具**，不要像营销页。每一处「我们承诺」都应该换成「你可以查」——界面上已经有好几个这样的链接，它们比任何文案都重要。
