# PeerProof 产品说明（给设计师）

写给接手视觉设计的人。每一屏都有手机版和电脑版截图、这一屏存在的理由、每个输入框和模块的含义。

截图在 `docs/screens/`，文件名规则 `序号-页面-mobile/desktop.png`。手机 390×844，电脑 1280×900，**都是真实链上数据渲染的**，不是占位图。

**图上的粉红色编号**（①②③…）和每节的模块表一一对应——看到表里写「③」，直接在图上找那个圈就行。

---

## 一、这个产品在做什么

活动报名时交一笔押金。到了现场，参与者**互相扫码作证**，合约自动结算：被证明到场的人拿回押金，**外加缺席者押金的分成**。

**主办方没有任何一个函数可以放款、扣款或收款。** 这是整个产品的立足点——不是「我们承诺不作恶」，是「代码里没有作恶的入口」。

### 为什么扫码能代表「到场」

三重约束叠加：

1. **对方的码 15 秒一换** —— 截图转发过去，两轮就废了
2. **每次见证必须附带场地信标签名** —— 会场屏幕上的码 2 分钟一换，你得在现场读到屏幕
3. **要被确认到场，你自己必须也给别人作过证** —— 所以每个被判定到场的账号，手里都握过一个活着的场地信标

远程串通不是不可能，但代价从零变成了「至少得有一个同伙真的到场并实时转发」。

### 1. 活动列表 `/events` —— 首页

![手机](screens/01-events-mobile.png)
![电脑](screens/01-events-desktop.png)

**这一屏回答**：现在有什么活动可以参加。

**模块**

| # | 模块 | 说明 |
|---|---|---|
| ① | 顶栏品牌 + `host one` | `host one` 去主办方后台。**任何人都能办活动，没有审核** |
| ② | 分区标题 `OPEN NOW` | 只有能参加的排在这里 |
| ③ | 活动卡片 | 整张卡可点，进入活动详情 |
| ④ | 卡片数据行 | 押金 / 已报名 / 需要几次见证 / 倒计时 |
| ⑤ | 已结束折叠区 | **收起但不删除**——公开记录是这个产品的论据，藏起来等于藏证据 |
| ⑥ | 底部说明 | 解释为什么标题可以随便写也不影响钱 |

**状态标签五种**

| 标签 | 含义 | 能否报名 |
|---|---|---|
| `Registering` | 报名中 | ✅ |
| `Starts soon` | 报名已截止，等见证窗口 | ❌ |
| `Checking in now` | 见证窗口开放，正在签到 | ❌（已报名的人去签到屏） |
| `Finished` | 结束，等结算 | ❌ |
| `Cancelled — refunded` | 人数不足，全额退款 | ❌ |
| `Settled` | 已结算 | ❌ |

**卡片上的四项数据**

- `50 MON to join` —— 押金
- `0/8 registered` —— 已报名 / 上限
- `2 vouches to count as present` —— 需要几个人给你作证
- `closes in 1d 4h` —— 倒计时

还有一行条件文案：`Needs 3 more to run — everyone is refunded otherwise`。**人数不够会全额退款**，这句消除报名者的顾虑。

**设计要点**：这是产品门面。卡片密度、状态标签的视觉权重、空状态的样子，都在这一屏定调。

### 2. 活动详情 `/?event=N` —— 未登录

![手机](screens/02-event-mobile.png)
![电脑](screens/02-event-desktop.png)

**这一屏回答**：这个活动是什么，押多少钱，规则是什么。

**模块**

| # | 模块 | 内容 |
|---|---|---|
| ① | 标题 + 简介 | 链上读的，主办方写的 |
| ② | 固定说明 | 「押一笔钱占位。到场、给周围的人作证，合约把钱还你——外加缺席者留下的那份」 |
| ③ | 三个数字块 | 已报名 / 需要几次见证 / 最低开办人数 |
| ④ | 押金卡 | 大字押金额 + 「由合约持有，不是主办方」+ 到场/缺席两种结果 |
| ⑤ | **身份选择区** | 见下。截图里是**降级状态**（无头浏览器没有 passkey），正是需要设计的那个 |
| ⑥ | 底部 | 「到场与否由房间里的人决定，主办方没有任何函数能放款、扣款、收款——**自己去查**」 |

**身份选择区**（未登录时）

三条路，按「对多少人有用」排序：

1. **`Create my key`** —— passkey（刷脸/指纹）。**体验最好**：一次授权，之后全程无弹窗
2. **`Continue with email`** —— 邮箱登录，Privy 自动创建钱包。**唯一不需要任何前置条件的路**
3. **`Use a wallet`** —— 已有 MetaMask 的人

**设计要点**：第 1 条不是所有设备都支持（桌面 Chrome、UC 浏览器都没有 WebAuthn PRF）。检测不到时这一屏会变成黄色提示 + 邮箱按钮优先。**这个降级状态要设计，它出现的频率不低。**

### 3. 活动详情 —— 已登录

![手机](screens/03-event-signed-in-mobile.png)
![电脑](screens/03-event-signed-in-desktop.png)

登录后身份选择区变成**一个主按钮**：

| # | 模块 | 内容 |
|---|---|---|
| ① | 主按钮 | `Stake 10 MON and register` ——**金额写在按钮上**，不让人点了才知道要付多少 |
| ② | 按钮下一行 | `balance 12.3 MON · you never see a gas prompt` |

「you never see a gas prompt」是 passkey 路径的卖点——派生出的密钥静默签名，不弹窗。

登录状态下方还有一行：`signed in as 0x7399…c621 · use a different account`。**密钥会被记住**（钱包/邮箱路径一天，passkey 路径仅当前标签页），所以刷新页面不会掉登录。那个链接是唯一的退出口——同一台设备上换账号时需要它。

**余额不足时**（见第 9 屏）按钮会禁用，上方出现一块橙色提示，说明还差多少、为什么押金不能由平台代付，并给出获取途径。

### 4. 主办方后台 —— 看板 `/organizer`

![手机](screens/04-organizer-dashboard-mobile.png)
![电脑](screens/04-organizer-dashboard-desktop.png)

**这一屏回答**：我的活动现在什么情况。

| # | 模块 | 内容 |
|---|---|---|
| ① | 标签切换 | `Dashboard` / `New Event` |
| ② | 四个数据块 | 已报名 / 已确认到场 / 托管中的金额 / 当前阶段 |
| ③ | `Held in escrow` | 下面那行 `not in your wallet` 是核心，不是装饰 |
| ④ | 参数卡 | 押金、最低人数、需要几次见证、状态 |
| ⑤ | **PAYOUTS 虚线框** | 「结算是自动的。你无法放款也无法扣款」 |
| — | 兜底签到区 | **只在同伴见证失败时才出现**，截图里没有 |

**`Held in escrow` 下面写着 `not in your wallet`** —— 这不是装饰，是整个产品要传达的核心。

**PAYOUTS 那个虚线框是刻意的空状态**：它描述的是「这里没有按钮」。demo 视频里有一个镜头专门停在这。**设计时别把它做成一个看起来可点的东西。**

**兜底签到区**（黄色警告块）只在「到场人数太少、同伴之间凑不够见证」时才解锁。这是**唯一**主办方的话有分量的分支，而且**依然不能让他拿到钱**。健康的活动里这一整块是不存在的。

### 5. 主办方后台 —— 建活动

![手机](screens/05-organizer-new-mobile.png)
![电脑](screens/05-organizer-new-desktop.png)

**两个模块，顺序是刻意的**：先说这是什么活动，再说规则。办活动的人**先想的是「这是个什么聚会」，不是「押金设多少」**——一上来就是六个数字输入框，读起来像配置页而不是邀请人的工具。

| # | 字段 | 含义 | 注意 |
|---|---|---|---|
| ① | **模块一：about the event** | 「What people see in the listing」 | |
| ② | `TITLE` | 活动名 | 不填就显示 `Event #20` |
| — | `DESCRIPTION` | 简介 | 最多 600 字符 |
| — | `LINK (OPTIONAL)` | 详情页链接 | |
| ③ | **模块二：the rules** | 「**Fixed once registration opens — including for you**」 | 这句是产品主张 |
| ④ | `DEPOSIT (MON)` | 每人押金 | |
| — | `CAPACITY` | 人数上限 | |
| — | `RUNS IF AT LEAST` | 最低开办人数 | ⚠️ **必须大于 vouches needed**，否则合约拒绝 |
| — | `VOUCHES NEEDED` | 需要几人作证才算到场 | 3 是常用值 |
| ⑤ | `DOORS OPEN IN (MINS)` | 多久之后开始签到 | **填 0 = 建完立刻能签到** |
| ⑥ | `RUNS FOR (MINS)` | 签到窗口开多久 | |
| ⑦ | ☑ `Take walk-ins` | 开场后还能不能继续报名 | 默认勾上 |
| ⑧ | `Create event` | | |

**时序**（这里之前写反了，已改）：

- 勾上 `Take walk-ins`：**报名一直开到活动结束**。路过看到活动的人可以当场加入。
- 不勾：报名在开场那一刻截止。传统 RSVP。

勾选框下面的说明文字会跟着状态换一句话，**这两句是产品态度，别删**：

> 勾上 —— People can still join after the doors open — the ones a room attracts on the night are often the ones worth keeping.
> 不勾 —— Registration closes when the doors open. Classic RSVP: decide in advance, or not at all.

**仍然值得设计一个时间轴示意**：现在是两个数字框加一个勾选框，三者的关系要在脑子里拼。这是这一屏最值得改进的地方。

**⑦ 下面那个橙色虚线框只在 `?dev=1` 时出现**，正式用户看不到，**不要设计它**。

**一个刻意的隐藏**：标题存在第二个合约里，如果那个合约还没部署，**提交时会自动带上部署**（按钮文字变成「Setting up descriptions…」）。用户永远不需要知道有这回事——「部署一个合约」是我们的基础设施问题，不该出现在想办读书会的人面前。

**建完之后**会显示一次性的**场地信标密钥**，要复制到会场设备上。这一屏也要设计——它是个「只显示一次、必须复制走」的关键时刻。

### 6. 签到屏 `/floor` —— 手机专用

![手机](screens/06-floor-mobile.png)
![电脑](screens/06-floor-desktop.png)

**这一屏回答**：我怎么证明我到了。

**这是唯一一个刻意锁死手机宽度的屏**——在电脑上打开也是一条窄栏，因为它只会被举在手里用。

| # | 模块 | 内容 |
|---|---|---|
| ① | 倒计时环 | 「refreshes in 12s」+ 走针圆环。上方是自己的二维码，**15 秒一换** |
| ② | `Scan someone` | 扫别人的码 |
| ③ | `Scan venue` | 扫会场大屏的码，成功后变成 `Venue ✓` |
| ④ | `VOUCHED FOR YOU` | 收到几个 / 需要几个，达标后变绿 |
| ⑤ | `confirmed present` | 全场进度条 |

**两个按钮的视觉层级是有讲究的**：没扫过场地码时，`Scan venue` 是**橙色警告色**，因为没有它，扫人是无效的。扫到之后变灰、打勾。

**使用环境**：站着、单手、房间光线可能很暗、摄像头开着。**触控目标 44px 起**，重要元素别贴在屏幕最底部。

### 6b. 签到屏 —— 还没到开场时间

![手机](screens/06b-floor-locked-mobile.png)
![电脑](screens/06b-floor-locked-desktop.png)

**同一个页面，早到的人看到的样子。**

| # | 模块 | 内容 |
|---|---|---|
| ① | 倒计时环 + 二维码 | **照常显示、照常轮换**。你的码现在就是活的 |
| ② | 「Doors open in」+ 大号倒计时 | 距离签到开始还有多久 |
| ③ | 一句解释 | 「Keep this page open; it unlocks on its own.」 |

**这一屏是被投诉出来的。** 原本这里是两个 35% 透明度的禁用按钮——测试的人看了一眼，得出的结论是「这个功能没做」，而不是「还没到时间」。**禁用态说不清「没有」和「还没」的区别**，所以改成了一个独立状态：倒计时说明它会自己解锁，二维码照常转说明这一页不是死的。

**设计要点**：倒计时是这一屏唯一的主角，要大。二维码留在上方不要藏起来——它证明页面是活的。**不要把这里做成错误态或空态的样子**，这是正常流程的一部分。

**另外**：如果在窗口之外扫了别人的码，扫描器会读出来并提示 `Code reads fine — check-in opens in 2h 14m.`，而不是报错。**码是对的，只是时候没到**——这两件事必须分开说。

### 7. 场地信标 `/venue`

![手机](screens/07-venue-mobile.png)
![电脑](screens/07-venue-desktop.png)

**这一屏回答**：证明「这件事发生在这个房间里」。

摆在门口的那块屏幕。显示一个**每 2 分钟更换的大二维码**，参与者扫它来证明自己在现场。

| # | 模块 | 内容 |
|---|---|---|
| ① | 主标题 | 「Scan me to check in」 |
| ② | 倒计时 | 「refreshes in Ns」——大二维码在它上方 |
| ③ | 信标地址 | 用来核对贴对了密钥没有 |
| ④ | `forget this key` | 换活动时清掉旧密钥 |

**截图是运行态。** 还有一个**未配置态**：一个输入框 + 「Paste the beacon key you were given when the event was created」+ `Start the display` 按钮。那一屏也要设计——主办方第一次打开看到的是它。

**它会跑在什么设备上不确定**——可能是备用手机，可能是笔记本，可能是投影仪。所以它**不能锁死手机宽度**：二维码要跟着屏幕放大（最大到视口高度的 70%），否则投出来隔几米就扫不到。

**设计要点**：这块屏幕会被远距离观看。字要大，对比要强，二维码周围留白要够。这是唯一一个「不给持有者看、给房间看」的屏。

### 8. 公开记录 `/verify`

![手机](screens/08-verify-mobile.png)
![电脑](screens/08-verify-desktop.png)

**这一屏回答**：凭什么相信结果。

| # | 模块 | 内容 |
|---|---|---|
| ① | 见证关系图 | 每个点是一个人，**每条线是一笔真实交易** |
| ② | 图例 | 实心=确认到场 / 空心=报名但未确认 / 数字=收到的见证数 |
| ③ | 结算算式 | 每人分到多少，链接到结算交易 |
| ④ | 逐笔见证列表 | 每一笔的交易哈希 |

**关系图是这个产品的论据本身**。它不是数据可视化装饰——它是「不用相信我们，每条线都能在区块浏览器上查到」的证据。

**设计要点**：这一屏要经得起评委点开逐条核对。节点密集时（50 人）的布局、线条交叉的可读性，是设计难点。

### 9. 余额不足 —— 活动详情的一个状态

![手机](screens/09-funding-mobile.png)
![电脑](screens/09-funding-desktop.png)

**这一屏回答**：我登录了，但我没有钱，怎么办。

这是邮箱登录留下的缺口。Privy 免去了「要有钱包」，但没有免去「要有钱」——一个从没接触过加密货币的人一键拿到账号，然后点报名失败，看起来像产品坏了。

| # | 元素 | 内容 |
|---|---|---|
| ① | 标题 | 「Add MON to register」——**是「充值」，不是「出错了」** |
| ② | 解释 | 差多少 + 「押金是你自己的钱进合约，**不能由别人代付**——正是这一点让缺席有代价」 |
| ③ | **充值区**（主体） | 「Send MON to your address」+ **地址二维码** + 可复制的完整地址 |
| ④ | **银行卡购买**（虚线框，灰） | 「Buy with a card」+ 右上角灰底标签 `not yet available` + 一句为什么 |
| — | 主按钮 | **禁用**，在整块下方 |

**这一屏改过一次，原因值得写下来。**

最早这里第一眼是「领测试币」的水龙头链接。那是**我们自己测试**才会做的事——去参加读书会的人不会去领测试代币。那样排版描述的是我们的测试环境，不是用户的处境。

现在的顺序按「今天真的能走通的方式」排：

1. **转账进来**——唯一在所有网络上都成立的办法，所以给它最大的版面
2. **银行卡购买**——**刻意做成不可点的**，这是用户要的「预留充值入口」
3. 水龙头——降到最下面一行小字，**只在测试网出现，设计时可以完全忽略**

**③ 的二维码不是装饰。** 手机上登录的人，没法把自己 42 位的地址粘进另一台设备的钱包里；扫码是现实中唯一走得通的路。编码的是 `ethereum:0x…@链号`，钱包 App 扫到会直接进「转账给」界面。

**④ 为什么是死的**：Monad 的银行卡通道还没开——MoonPay 已建好原生 MON 但处于暂停状态，Stripe 的目标链列表里没有 Monad。**放一个点开什么都买不到的按钮，比明说更糟。** 等哪家上了 MON，这个框变成可点的链接，**这一屏其他部分一个字都不用改**。

**设计要点**：这个状态出现的频率会很高——每个用邮箱登录的新用户都会撞上。它不该像错误，该像「下一步做什么」。目前整块用的是橙色警告色，**这一点值得重新考虑**：充值是正常流程，不是异常。

### 10. 结算与领款 —— 签到屏的最终状态

![手机](screens/10-payout-mobile.png)
![电脑](screens/10-payout-desktop.png)

**这一屏回答**：我拿到了多少，凭什么。

**这是整个产品的情绪高点**，也是它和所有其他活动报名工具拉开差距的地方——**「到场的人拿回的比投入的多」是一个数字，不是一句承诺**。

截图里是真实的链上结果：4 人报名，3 人到场，1 人缺席。到场的人各拿回 **13.33 MON**（10 押金 + 3.33 缺席者分成）。

| # | 元素 | 内容 |
|---|---|---|
| ① | `PAID OUT` | 绿色小标 |
| ② | 大数字 | 到手总额 |
| ③ | 拆解 | 「你的 10 MON 押金退回，**外加 3.33 MON** 来自没来的人」 |
| ④ | 归属说明 | 「没有人批准这件事。分配比例在窗口关闭时就定死了，由谁给谁作证决定」 |
| — | 交易链接 | `see the transaction ↗` |

**设计要点**：这一屏之前只是一个变灰的 `Claimed` 按钮。它值得是整个流程里最有分量的一屏——**但分量要来自数字本身和可核验性，不要来自庆祝动效**。这个产品的气质是「你可以查」，不是「恭喜发财」。

上面还有两个模块也在这一屏：

- **`VOUCHED FOR YOU 2/2` + `You count as present`** —— 见证进度，达标后变绿
- **`confirmed present 3/4`** —— 全场进度条

## 三点五、三条登录路径（设计重点）

这是整个产品**分支最多、最容易设计漏**的地方。用户看到哪条路，**取决于他的设备有什么**——不是他选的。

### 先划清边界：哪些能设计，哪些不能

| 界面 | 归属 | 能不能改样式 |
|---|---|---|
| 身份选择区（几个按钮） | **我们的** | ✅ 完全可设计 |
| 加载中文案（`Creating your key…` 等） | **我们的** | ✅ |
| 错误提示 | **我们的** | ✅ |
| 系统刷脸/指纹弹窗 | 操作系统 | ❌ 完全不可改 |
| MetaMask 连接和签名弹窗 | MetaMask | ❌ 完全不可改 |
| Privy 登录弹窗 | Privy | 🟡 只能调主色和明暗，布局不可改 |

**设计师只需要设计第 1–3 行。** 后面三行是既成事实，但**必须知道它们存在**，因为它们打断流程、改变节奏。

---

### 路径 A：passkey（体验最好，覆盖最窄）

```
点「Create my key」
   ↓
【系统弹窗】刷脸 / 指纹          ← 不可设计
   ↓
完成。之后全程无任何弹窗
```

**只有这条路做到了「签到时零打扰」**——派生出的密钥在本地静默签名，15 秒换一次码也不会弹窗。

**支持范围**：iPhone Safari（iOS 18+）、Android Chrome。**桌面浏览器基本都不支持**（需要 WebAuthn PRF 扩展）。

### ⚠️ 那个「第二次签名」，两条路都有

用户刚登录完，会**再弹一次签名**，内容是：

```
PeerProof attendance key

Signing this derives the key that signs your attendance codes.
It does not authorise any transfer.

Contract: 0x289a…
Event: 4
```

**这是产品设计的一部分，不是多余步骤。** 它用一次签名派生出「签到码专用密钥」，之后扫码全程静默——**没有它，每扫一个人都要弹一次窗，15 秒一换的码就完全没法用**。

**但对用户来说这是个困惑点**：「我刚登录过了，怎么又要签？」

**设计需求**：在点击按钮之前或之后，用**我们自己的界面**解释这一步。现在完全没有铺垫，用户直接撞上一个第三方弹窗。可以是按钮下方一行小字，也可以是点击后的过渡态。文案要点：

- 这一步**不花钱、不授权转账**（弹窗自己也写了，但用户不一定看）
- 换来的是**之后扫码不再弹窗**
- 一个活动只需要签一次

### 路径 D：什么都没有（死路）

![手机](screens/12-identity-none-mobile.png)
![电脑](screens/12-identity-none-desktop.png)

没有 passkey、没有钱包、也没配 Privy 时，页面显示：

| # | 模块 | 内容 |
|---|---|---|
| ① | 橙色提示块 | `This device can't hold a passkey key. Open this on a phone, or install a browser wallet.` |

下方还有一个折叠的 `why?`，展开是两段解释（PRF 扩展是什么、为什么钱包路径要每次确认）。**默认折叠是刻意的**——落到这一屏的人需要的是出路，不是原理。

**这是当前唯一真正的死路。** 配好 Privy 之后它不该再出现——但如果 Privy 服务挂了或者域名白名单没配对，用户就会落到这里。

**设计需求**：这一屏要**明确告诉用户去哪**，而不是只说「你不行」。现在的文案已经在做这件事，但视觉上它和普通警告长得一样，没有「这是终点，请换个方式」的分量。

### 一张表总结

| | passkey | 邮箱 | 钱包 |
|---|---|---|---|
| 需要什么 | 支持 PRF 的浏览器 | **什么都不需要** | 装了 MetaMask |
| 弹窗次数 | 1 次（刷脸） | 3 次（邮箱/验证码/签名） | 2 次（连接/签名） |
| 扫码时 | **零打扰** | 每次确认 | 每次确认 |
| 登录后有钱吗 | 看用户自己 | **没有**，必然撞上第 9 屏 | 通常有 |
| 谁会走这条 | 手机用户 | 没接触过加密货币的人 | 已有钱包的人 |

**设计时的排序原则**：邮箱排在钱包前面。有钱包的人两条都能走，**没钱包的人只有邮箱这一条**。

## 四、还没做的部分

原来列了五处缺口，三处已补（第 9、10 屏，以及充值入口文案）。剩下两处**没有截图，因为还不存在**——下面是设计需求，不是描述。

### A. 报名成功的确认时刻

**现在是什么样**：点「Stake 50 MON and register」→ 交易上链 → 按钮区直接换成「Go to the floor」。押金离开钱包这件事**没有任何交代**。

**为什么要做**：这是用户第一次真的掏钱。50 MON 从钱包出去了，界面却像什么都没发生。**在一个主打「钱不在主办方手里」的产品里，钱去哪了这一刻必须说清楚。**

**必须传达**（按重要性）：

1. **钱到了合约，不是主办方** —— 这是产品的全部主张，在掏钱这一刻说最有力
2. **接下来该干什么** —— 报名截止时间、见证窗口什么时候开
3. **怎么拿回来** —— 到场并被 N 个人作证

**可用数据**：交易哈希、押金额、区块浏览器链接、报名截止时间、见证窗口开始时间、需要几次见证、当前已报名人数。

**约束**

- 这是**一次性时刻**，刷新后就该变成常规的「已报名」状态，不能每次进页面都弹
- 手机上单手操作，主按钮（去签到屏）要落在拇指区
- **别用庆祝动效**。这个产品的气质是「你可以查」，礼花和这个基调冲突
- 交易哈希要能点开，**可核验性是这里的情绪来源**

**参考现有元素**：第 10 屏（结算）是同一类「钱动了」的时刻，可以呼应，但那是收钱、这是付钱，情绪不同。

---

### B. 见证成功的即时反馈

**现在是什么样**：扫到一个人 → 交易上链 → 顶部飘一个 toast（2.6 秒消失）→ `VOUCHED FOR YOU` 的数字 +1。

**为什么要做**：**这是 demo 视频里最关键的一个镜头**。整个「为什么必须是 Monad」的论证就靠这一下——A 扫了 B，两台设备在一秒内同时更新，屏幕上显示真实上链耗时。现在这个瞬间在视觉上完全没有分量。

**必须传达**

1. **对方是谁** —— 扫到的地址（缩写形式）
2. **上链耗时** —— 真实毫秒数，这是硬证据，**必须醒目**
3. **双方都得分** —— 一次扫码，两个人的计数都 +1，这是合约的设计，界面上要体现
4. **离达标还差几个**

**可用数据**：交易哈希、确认耗时（毫秒）、对方地址、自己当前收到的见证数 / 需要数、对方的新计数。

**约束**

- **必须在 15 秒内看完**，因为码 15 秒一换，用户马上要扫下一个
- 会场光线可能很差，**对比度要高**
- 会被摄像机拍，**数字要大到能上镜**
- 失败也要有对应状态：码过期、重复扫同一个人、场地码没扫
- 不能挡住摄像头取景框太久——扫完还要接着扫

**这一屏的成败标准**：把手机屏幕录下来，单看这几秒，能不能让人相信「这真的是 300 毫秒上链」。

## 六、给设计的一句话

这个产品的全部主张是「**不用相信任何人，自己验证**」。

所以视觉上应该**克制、可信、像工具**，不要像营销页。每一处「我们承诺」都应该换成「你可以查」——界面上已经有好几个这样的链接，它们比任何文案都重要。
