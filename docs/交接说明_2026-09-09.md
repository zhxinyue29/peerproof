## 一、必须你决策的两件事（按紧急度）

### 1. 押金金额定错了，gas 会吃掉整个押金池 🔴

实测数据（Monad 计价规则下，非以太坊默认）：

| 操作 | gas | 按当前 102 gwei 折算 |
|---|---|---|
| `attest` 单笔见证 | 152,799（峰值 184,006） | **≈ 0.0156 MON** |
| `register` 报名 | 92,890 | ≈ 0.0095 MON |
| `claim` 领取 | 83,933 | ≈ 0.0086 MON |
| `settle` 结算 | 53,558 | ≈ 0.0055 MON |
| `createEvent` | 102,856 | ≈ 0.0105 MON |

**问题**：50 人各扫 3 次 = 150 笔见证 = **2.34 MON gas**，而押金池 = 50 × 0.05 = 2.5 MON。gas ≈ 押金池全部。

**根因不是 gas 贵，是我把押金定得太小。** 0.05 MON 按 MON 现价大概只值几分钱，作为「守约装置」根本不痛，而且被 gas 比下去了。

**要你做的**：查一下 MON 现价，然后按**法币目标值**反推押金。建议目标 **¥5–10 一份押金**（这是能让人心疼、又不至于不敢试的量级）。

约束条件：`押金 ≫ 单笔gas × 人均见证次数`，也就是押金至少要是 0.05 MON 的**几十倍**。

我没有替你定，因为这取决于 MON 现价，而且直接影响 demo 要花多少真钱。

### 核心合约：AttendanceEscrow.sol

24 项测试全部通过，覆盖正常路径、防刷、边界、退款。

**一个关键设计突破**：滚动见证码用 **passkey PRF 派生的 secp256k1 密钥**签名，合约用 `ecrecover` 验证（约 3000 gas）。

这样做的两个好处：

1. **完全绕开 P256 预编译的不确定性**。如果用 passkey 原生的 P256 签名，需要 RIP-7212 预编译，而 Monad 支持情况还没确认（我探测 0x100 返回空，但预编译本来就没 bytecode，这个测试不算数，还在等研究结果）。用 secp256k1 就没这个依赖。
2. **依然满足 Mera 那个 bounty** 要的「creative non-wallet use of PRF-derived key material」——这正是 PRF 派生密钥的非钱包用途。

**函数一览**：

| 函数 | 谁能调 | 作用 |
|---|---|---|
| `createEvent` | 任何人 | 建活动。**主办方不出资、也永远取不出钱** |
| `register` | 任何人 | 交押金报名，同时登记自己的 attestKey |
| `attest` | 已报名者 | 提交对方的滚动码，**一次扫码双方各 +1** |
| `organizerCheckIn` | 主办方 | 兜底签到，**只在同伴见证不足时解锁** |
| `cancelForQuorum` | 任何人 | 报名不足最低成行人数 → 全员可退 |
| `settle` | **任何人** | 窗口结束后锁定分配（故意不设权限） |
| `claim` | 已报名者 | 提取应得款（pull payment，防重入） |

**已实现的关键约束**：

- 每个无序配对只能见证一次（`pairUsed`），A↔B 反向也拦（测试覆盖）
- 不能自己见证自己
- 滚动码只在当前和上一个 15 秒周期内有效 → 超过约 30 秒的截图作废
- 拒绝 ECDSA 高位 s 值（防签名可塑性）
- **主办方兜底只在 `peerConfirmed <= k` 时解锁**——健康房间里这个函数直接 revert，主办方结构性地无法干预正常结算
- 确认人数为 0 → 全员退款，不乱判
- `test_organizerCannotReceiveFunds` 显式验证主办方拿不到钱

**结算数学已验证不留尾款**：10 人报名 / 4 人确认到场 → 每人 0.125 MON，合约余额精确归零（`test_peerAttestation_settlesWithoutOrganizer` 断言 `address(esc).balance == 0`）。

## 三、Monad 特有的坑（研究得来，都影响实现）

### 🔴 按 gas limit 计费，不是按实际用量

`gas_paid = gas_limit × price_per_gas`。padding「保险起见多给点」是真花钱。

**对我们的影响**：赞助 gas 的 relayer 必须**写死已知操作的 gas limit**，不要调 `eth_estimateGas` 然后加 buffer。`attest` 峰值 184,006，写死 200,000 就行。

### 🟡 我的 storage 布局没利用 Monad 的聚集访问折扣

Monad 按「页」预热存储（128 槽/页，8,100 gas/页），冷账户访问从 2,600 涨到 10,100。这就是 9 月 4 日那次「聚集访问 gas 降 98%」升级的机制。

**但我现在的写法没吃到这个折扣**：`attestCount`、`isConfirmed`、`attestKeyOf`、`hasClaimed` 是四个独立 mapping，同一个参与者的数据被哈希到四个随机槽，散落在不同页。

**优化方案（gas 优化第一优先级）**：把每个参与者的状态打包进**一个** slot：

```
address attestKey (20 bytes) + uint32 attestCount (4) + bool registered/confirmed/claimed (3) = 27 bytes
```

27 < 32，一个槽装得下。这样 `attest` 从触碰 6+ 个槽降到 3 个（subject 1 + attester 1 + pairUsed 1），**预计能把 152,799 砍掉接近一半**。

这个优化还有叙事价值：它本身就是「为 Monad 的存储模型专门设计」的证据。

### 其他已知坑

- **`eth_getLogs` 单次上限 100 个块**（rpc.monad.xyz / monadinfra），Alchemy 和 Ankr 端点是 1,000。Envio HyperSync 走自己的通道，不受此限。
- **没有全局 mempool**，`eth_getTransactionByHash` 对 pending 交易返回 null。**前端确认逻辑绝对不能依赖 mempool 可见性。**
- **不支持 blob 交易（type 3）**，type 0/1/2/4 支持。
- 单笔 gas 上限 30M、单块 150M、500M gas/s。按 `attest` 152,799 算，理论上**一个块能装约 980 笔见证**——我们那 150 笔洪峰完全在能力内，这个数字可以写进 pitch。
- **不要用 `foundry.category.xyz` 那个安装器**，也不要 `foundryup --network monad`——那是废弃的 Monad Foundry 分支，很多博客还在传。用官方 stock Foundry（我装的就是）。
- 调试/trace 在 rpc1（Alchemy）和 rpc3（Ankr）上被禁用。
- 有个 Monad 特有的 **reserve balance** 概念要读：https://docs.monad.xyz/developer-essentials/reserve-balance

#### 所以方案要改：我们其实不需要 paymaster

关键推论：**我们的目标用户本来就持有 MON**（定位已收窄，见第一节）。既然他有 MON，他就能付自己的 gas。

而「用户看不到 gas」这个体验目标，**不需要靠赞助实现，只需要不弹窗**：

```
Mera passkey → PRF → secp256k1 密钥（刷脸一次派生）
    ↓
之后每笔交易在 JS 里本地签名，不再弹生物识别
    ↓
用户从头到尾没见过 gas 弹窗，但 gas 是他自己付的
```

**这样可以整条砍掉 paymaster、bundler、EntryPoint、gas 池**——四个依赖，每个都是 demo 里可能炸的点，而且省掉付费订阅。

Mera 直接给的就是一个能用 viem 签名的 EOA，`toViemAccount()` 之后当普通账户用即可。

**如果后来确实需要赞助**（比如想服务真正的零 MON 用户），再加 ERC-4337：EntryPoint v0.7 `0x0000000071727De22E5E9d8BAf0edAc6f37da032` 已在主网且实测活跃（13 分钟内 669 笔 userop）。别用 v0.9（零使用量，部分 bundler 仍视为 WIP）。

💰 **仍然建议申请**：Alchemy × Monad grant，最高 $10K credits — https://www.alchemy.com/monad-grant 。免费额度不够，但 grant 是另一回事，而且对着 Alchemy 那个 bounty。

### 🔴 必须第一天验证的未决问题：10 MON 储备金是否也管普通 EOA

Monad 有个 `user_reserve_balance`，**当前设为每个 EOA 10 MON**（https://docs.monad.xyz/developer-essentials/reserve-balance ）。

已确认的部分：**被 7702 委托的 EOA** 任何降低余额且结果低于 10 MON 的交易**无条件 revert**，且不能使用「清空账户例外」。

**没确认的部分（关键）**：**普通未委托的 EOA** 有「清空账户例外」，但一个只有 1 MON 的普通 EOA，能不能正常发一笔花掉 0.05 MON 的交易？文档措辞含糊。

**为什么这决定架构**：

- 如果普通 EOA 不受限 → 上面那个「砍掉 paymaster，Mera EOA 直接用」的方案成立 ✅
- 如果普通 EOA 也卡 10 MON → 用户必须常驻 10 MON，**0.05 MON 量级的押金根本不可行**，必须改用 ERC-4337 合约账户（合约账户明确豁免储备金）

**怎么验**：往一个空地址转 0.5 MON，然后从它发一笔转出 0.05 MON 的交易，看是否 revert。花几毛钱，五分钟，但结论决定整个账户层怎么搭。**这是现在的第一优先验证项。**

（另外确认：7702 委托上下文里 `CREATE`/`CREATE2` 被禁用——任何会部署合约的 delegate 会静默失效。我们不走 7702 就无关。）

## 五、Passkey / 账户层研究结果（已回，含一条紧急项）

### 🔴 紧急且不可逆：域名必须现在就定死

**passkey 绑定 rpId（域名）。域名一换，所有已创建的 passkey 账户永久无法复现。** Mera 官方原话：「After a domain migration, passkey accounts can no longer be reproduced.」

**具体风险**：如果你先在 Vercel 的 preview URL（`xxx-git-abc.vercel.app`）上创建 passkey 做测试，然后换到正式域名，**那些账户和里面的钱全部永久丢失**。

**要做的**：**在任何人创建第一个 passkey 之前**，把最终域名定下来并一直用它开发。这件事没有补救措施。

顺带：**passkey 丢了 = 钱丢了**，Mera 明确把恢复机制的责任留给你。demo 的测试账户别放多余的钱。

### ✅ Mera 是真的，而且和我的合约设计天然契合

| | |
|---|---|
| 文档 | https://mera.category.xyz/ |
| GitHub | https://github.com/category-labs/mera |
| npm | `@category-labs/mera` **v0.2.0** |
| 许可 | MIT OR Apache-2.0（双许可，宽松） |
| 出品方 | Category Labs（Monad 核心开发公司） |

**关键发现：Mera 不是 ERC-4337，不是智能账户，不部署任何合约。** 它是一个 `passkey → PRF → BIP-39/BIP-32 → secp256k1 EOA` 的密钥派生库。

**这正好是我合约里 attestKey 的形态。** 我写的 `ecrecover` 验证路径，Mera 的 `toViemAccount(session)` 可以直接对接，**合约一行都不用改**。这个契合不是我预先设计的，是运气好。

```js
const { prfOutput, credentialId } = await getPasskeyPrfOutput({ rpId });
// prfOutput = 32 字节，确定性
```

默认 salt 是 `sha256('mera.prf.salt.v1')`，跨版本稳定。派生要自己装 `@scure/bip32` + `@scure/bip39`。EVM 路径 `m/44'/60'/0'/0/{i}`。密钥在 `session.end()` 时清零。

⚠️ **v0.2.0 是 preview 软件**，官方声明 v1.0 前 API 可能变，只发布过 2 个版本，GitHub 约 30 星。

### ⚠️ 我一个假设被推翻了：P256 预编译其实是活的

我当初选 PRF→secp256k1 的理由是「绕开 P256 预编译的不确定性」。**这个理由不成立了**——Monad 实现了 **EIP-7951**（取代 RIP-7212），地址 `0x0100`，实测有效签名返回 1，**只要约 7,251 gas**。（我之前用 `cast code` 探测返回空，那个测试方法本身是错的，预编译没有 bytecode。）

**但这个设计仍然是对的，理由换成了一个更强的：**

> 滚动码每 15 秒换一次。如果用 passkey 原生的 P256 签名，**每 15 秒要弹一次 Face ID**，体验直接毁掉。PRF 派生密钥只需刷脸一次，之后在 JS 里本地签名，无感。

而且 `ecrecover` 约 3,000 gas 比 P256 预编译的 7,251 更便宜，在 150–250 笔见证的量级上有意义。

**所以：合约不改，但 pitch 和文档里的理由要换成「不能每 15 秒刷一次脸」。** 这个理由评委更容易认同。

### 🟡 真正的风险是 PRF 的浏览器覆盖率

**能用**：iCloud Keychain（Safari 18 / iOS 18+ / macOS 15+）、Chrome 132+（Android 和已登录的桌面）、Windows 11 25H2 + 2026-02 更新、1Password ≥2.26.1、Proton Pass

**不能用**：**Chrome 桌面的本地 profile passkey（完全没有 PRF）**、Bitwarden 桌面 Chrome、Dashlane、NordPass、Microsoft Password Manager、Android 版 Firefox

**这是整个项目的第一风险，比链上基础设施大得多。** 一个用 Chrome 桌面本地 passkey 的评委，点开你的 demo 会直接卡住。

**必须做**：能力检测 + 降级路径。检测不到 PRF 时退到普通钱包连接（或 Privy 嵌入式钱包），并在界面上说明。**demo 视频用 iPhone 录**（iCloud Keychain 是覆盖最好的）。

### ✅ 账户层推荐路径（避开 10 MON 储备金限制）

```
Mera passkey → PRF → secp256k1 EOA → toViemAccount()
    ↓ 作为 owner
ZeroDev Kernel v3.1 + ECDSAValidator（两者主网都已部署）
    ↓
```

## 五之二、合约审查结果（第三个 agent）

### ✅ 已修：一个真 bug（竞态导致到场者被坑）

`settle()` 原来只要求 `block.timestamp >= attestClose`，且任何人可调。于是人少的场景下，窗口一关任何人立刻调 `settle()` → `confirmed == 0` → 状态变 `Cancelled` → 全员只退押金，**主办方兜底签到永久失效**（它要求 `status == Open`）。

**这把你上次反对的那个不公平从竞态里放回来了**——到场的两个人白跑。

已修：加了 `FALLBACK_WINDOW = 1 hours`。同伴已达标的房间（`peerConfirmed > k`）立刻可结算；需要兜底的房间必须等这个宽限期过完。回归测试 `test_settleBlockedUntilFallbackWindowElapses` 覆盖。现在 **26 项测试全绿**。

### 🔴 最大缺口：合约里没有「场地信标」，远程串通完全可行

我们在讨论里说过「主办方广播一个现场信标码作为见证的必要盐值」，但**我没有把它实现进合约**。当前的漏洞是实打实的：

```
滚动码由「被见证者」的 attestKey 签名，由「见证者」提交
    ↓
所以 B 只要把签名通过微信/邮件发给 A，A 就能提交
    ↓
15 秒过期只能拦住随手转发，拦不住脚本：
B 的脚本持续签当前 epoch 发到共享服务器，A 的脚本取来提交
    ↓
全自动、全远程、四个人在家就能瓜分全场押金池
```

**而且我们的激励比 Kickback 更糟**：Kickback 里缺席者的钱归主办方，我们的归到场者——**等于我们主动为这个攻击付钱。**

**修法（约 40 行，EIP-712，一天能做完）**：

```
场地屏幕持一个临时密钥对，QR 里含 epoch + 场地签名
    ↓
attest() 要验两个签名：被见证者的 + 场地的
    ↓
没在现场看过场地屏幕，就产生不出有效见证
```

这样至少强制有人物理到场。**依然不完美**——现场一个同伙可以把场地码转发给远端。但门槛从「零成本」升到「必须有人真的去」。

**这条要写进 Limitations，别等评委问：**

> Rotation plus a venue-bound salt raises the cost of remote collusion from zero to "at least one confederate must physically attend and relay." It does not eliminate it. Onchain proof of physical location is an open problem; NFC/UWB attestation is future work.

**优先级：这是第一优先的合约改动**，比 gas 优化重要——gas 只是贵，这个是机制不成立。

### 🟡 我的判定用的是朴素阈值，不是 K-core

我现在的逻辑是「收到 ≥K 个见证就算到场」，**但它会把「来自本身没到场的人的见证」也算进去**。

正确的形式化叫 **K-core**：最大的集合 S，使 S 内每人都有 ≥K 个来自 S 内部的见证。好消息是它**唯一且最大**（不像最大团那样 NP 难），O(V+E) 的剥离算法就能算。

但**不要在链上算**。agent 查证：BrightID 全部图分析在链下跑，Circles UBI 链上只做路径查找，没人在链上做全局图分析。

**推荐做法（submit-and-challenge）**：任何人提交一个候选集合 S（用位图编码），合约只验「S 内每人都有 ≥K 个 S 内见证」——单次 O(|S|+E)，很便宜；**不验最大性**。挑战窗口内任何人可以提交更大的合法 S 来替换。

安全性理由：非最大的 S 从不产生错误结算，只会**少算**到场者；而任何被漏掉的合法到场者有直接经济动机自己提交更大的集合。**最大性靠激励拿到，不靠 gas。**

这是 V2 优化，不是 V1 阻塞项。朴素阈值 + 场地信标已经能交付。

### ✅ 可复用的开源代码（你最初问的就是这个）

**EAS 没有部署在 Monad 主网**（26 个网络的部署目录里没有 143，`monad.easscan.org` DNS 都解析不了）。所以自己写专用合约是对的——而且 EAS 每条见证要写 5–7 个存储槽，我们只要 1 个位 + 1 个计数器。

| 要做的东西 | 抄哪里 | 许可 |
|---|---|---|
| 押金 + 报名 + 参与者索引 | [wearekickback/contracts](https://github.com/wearekickback/contracts) 的 `AbstractConference.sol` | MIT |
| **出席位图编码 + 位计数** ← 最值得抄的一个想法 | 同上，`finalize()` 里的 uint256 位图 | MIT |
| Merkle 领取 + 防重复 + 叶子双哈希 | [unlock-protocol 的 Kickback.sol](https://github.com/unlock-protocol/unlock/blob/master/smart-contracts/contracts/utils/Kickback.sol)（只 45 行） | MIT |
| ETH 转账 / 重入锁 / 位图 / EIP-712 / 签名校验 | Solady 的 `SafeTransferLib`、`ReentrancyGuard`、`LibBitmap`、`EIP712`、`SignatureCheckerLib` | MIT |
| 场地滚动码 | **自己写**，EIP-712 over 时间分桶 epoch | — |

还值得花 15 分钟读的：[Kickback 的自审报告](https://github.com/wearekickback/contracts/blob/master/doc/SelfAuditV084.md)。里面记了两个真实事故（2017-02 转账后改状态导致重入、2016-09 `setLimitOfParticipants` 漏了权限修饰符被人利用），而且**他们自己就点出了串通攻击，只是因为押金小而没管**——这个免责我们用不了。

⚠️ **许可陷阱**：[Uniswap 的 merkle-distributor](https://github.com/Uniswap/merkle-distributor/blob/master/contracts/MerkleDistributor.sol) 是最经典的 BitMap+MerkleProof 领取合约，但它是 **GPL-3.0**——抄它你整个仓库就得 GPL。用 Unlock 那个 MIT 版本，行数还更少。

⚠️ 另外这几个仓库**没有 LICENSE 文件**，只能读不能抄：`mcortesi/poap`、`socathie/zkOTP`、`cursive-team/zk-summit`、`indexed-finance/dividends`。

✅ 顺带确认我一个选择是对的：**OpenZeppelin 的 `PullPayment`/`PaymentSplitter` 在 v5 里已被删除**（只在 release-v4.9 里有）。我手写 pull payment 是正确做法。

### 一个正面结论

> 「主办方对放款没有任何权力」这个要求，**没有任何现成合约可以 fork**。Kickback 和 Unlock 都是管理员调 `finalize()` 或发布 Merkle 根。

也就是说结算逻辑必须自己写——**这恰好证明了这个项目的创新点是真的**。而且 Unlock 官方博客里说缺席者的钱「未来甚至可以分给到场者」，**我们做的就是他们说了但没做的那件事**。这句话可以直接引用进 pitch。

## 五之三、赛道可能要重选（新证据，不是我又改口）

**Track 4「Trust, Identity & AI Infrastructure」的官方页面把我们的用例逐字列为最佳示例：**

> "Passkey-native accounts using **P256 and WebAuthn**, no seed phrase."

我此前三次推荐 Consumer Products & Payments，理由是 Trust/Identity 赛道要的是「protocol-level primitives」而我们交的是 App。**这条原文推翻了那个推理**——官方自己把 passkey 账户当成该赛道的典型项目。

**但有个讽刺的地方**：我们现在的方案（Mera：PRF → secp256k1）**根本不碰 P256**。agent 明确指出 Mera「never touches the `0x0100` precompile」。所以如果打 Track 4 的 passkey 牌，我们用的恰好是唯一一种**不是 P256-native** 的 passkey 方案。

**这是个真决策，我不替你做。三个选项：**

| 选项 | 赛道 | 代价 |
|---|---|---|
| A. 维持现状 | Consumer & Payments | 稳，但放弃 Track 4 那个逐字匹配 |
| B. 账户层换成 P256 WebAuthn（Coinbase Smart Wallet） | Trust/Identity 或 Consumer | 见下，**顺带消灭 PRF 覆盖率风险** |
| C. 混合：账户层用 P256，滚动码仍用 PRF | 任一 | 最强但工作量最大 |

**选项 B/C 有个我之前没意识到的巨大好处**：普通 WebAuthn（不带 PRF）是**普遍支持**的。换掉账户层就能干掉「Chrome 桌面本地 passkey 完全没有 PRF」这个第一风险。

而且现成件已经全部在 Monad 主网部署好了：

| 合约 | 地址 | 状态 |
|---|---|---|
| Coinbase SmartWalletFactory v1.1 | `0xBA5ED110eFDBa3D005bfC882d75358ACBbB85842` | ✅ 与以太坊/Base **字节完全一致** |
| Coinbase SmartWalletFactory v1 | `0x0BA5ED0c6AA8c49038F819E587E2633c4A9F428a` | ✅ 同上 |
| Alchemy WebAuthnValidationModule | `0x0000000000001D9d34E07D9834274dF9ae575217` | ✅ 同上 |
| Alchemy ModularAccount v2.0.0 | `0x00000000000002377B26b1EdA7b0BC371C60DD4f` | ✅ 同上 |

**Coinbase 的 `WebAuthn.sol` 硬编码了 `address(0x100)`，staticcall 后按返回值长度自动回退**——真正的运行时探测，无需调用方传参，**在 Monad 上会自动走快路径**。许可 **MIT**。唯一限制：只支持 **EntryPoint v0.6**。

Alchemy MAv2 用的是**同一个 Coinbase 库**，支持 EP v0.7 + 7702，但许可是 **GPL-3.0**——copyleft，会约束你的仓库。

**实测 gas 更正**：P256 预编译是 **6,900 gas**，不是网上到处引用的 3,450（那是旧的 RIP-7212 定价，EIP-7951 改成了 6,900）。纯 Solidity 的 Daimo 验证器要 347,858 gas，**50 倍差距**，所以在 Monad 上完全不需要 Solidity 回退。

顺带：**FreshCryptoLib 已被作者本人标记废弃**，Safe 也因为已知 bug 移除了它的 FCL 验证器。

**另一个印证**：Mera 在桌面 Chrome 上（Google 密码管理器之外）直接报 `PRF_UNAVAILABLE`。这不是理论风险，是确定会发生。

### 我的倾向

**选项 C，但赛道留在 Consumer & Payments。**

理由：账户层换 P256 能干掉第一风险，这个收益是实的；但赛道不该跟着passkey 走，因为**我们项目的核心创新是同伴见证机制，不是 passkey 账户**。打 Track 4 会让评委拿我们和纯身份基础设施比，而我们的重心在钱和机制上。

passkey 只是让产品可用的手段。**别让手段决定赛道。**

不过这条你可以推翻我——如果你觉得「passkey-native 账户」比「同伴见证」更好讲，Track 4 那句逐字匹配确实很值钱。

### 其他确认

- **EntryPoint v0.7 是 Monad 上的事实标准**：约 1000 个块内 v0.7 有 455 笔 UserOp，v0.8 只有 9 笔，v0.6 只有 1 笔。
- **没有官方 Monad passkey 起始模板**。最接近的第三方是 [nishuzumi/monad-passkey-4337-starter](https://github.com/nishuzumi/monad-passkey-4337-starter)（MIT、EP v0.7、自写 `Passkey4337Account`），但**针对测试网 10143**，且没有文档说明预编译用法。
- Safe 核心在 143 上全部部署（v1.4.1/v1.5.0 canonical），Transaction Service 也活着，但**passkey 模块的 `SafeWebAuthnSignerFactory` 没有代码**——要自己部（可以，Safe Singleton Factory 在 143 上是活的）。Safe passkey 模块许可是 **LGPL-3.0**。

## 附：我做了但你可能不同意的判断

老实列出来，你可以推翻：

1. **改了你的 `~/.bashrc`** —— 不改的话 node 用不了。撤销方式在上面。
2. **`evm_version` 用 `network = "monad"` 自动选择**，没有手写 `"osaka"` —— 因为那个目标会变，写死会过期。
3. **`settle()` 做成任何人可调** —— 这既规避了 CRE 审批风险，也让「结算不需要任何人动手」这个主张更硬。副作用是任何人都能触发结算，但窗口关闭后才允许，且分配逻辑固定，没有可操纵空间。
4. **主办方兜底签到的解锁条件设为 `peerConfirmed <= k`** —— 也就是同伴确认人数不超过 3 时才解锁。这个阈值是我拍的，你可能想设得更严或更松。
5. **删掉了 Foundry 默认生成的 `Counter.sol` 及其测试脚本** —— 模板垃圾文件。
6. **押金我在测试里仍然用 0.05 MON** —— 因为改这个要等你定金额，测试数值只是占位，不影响逻辑正确性。
